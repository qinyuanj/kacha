# 本地优先的桌面客户端取代 Web 路线

2026-11-14 决定（[用 MyGo 建立本地优先客户端的第一竖切](https://github.com/qinyuanj/kacha/issues/124)）：Kacha 回到本地优先的 Windows 桌面客户端，[ADR 0018](0018-web-app-replaces-desktop-client-with-server-side-task-directories.md)「Web 版取代桌面客户端，任务目录放在服务端」的决定就此被取代。画板、任务目录与设置回到用户当前这台电脑的用户数据根，查看、编辑与组织画板不依赖网络或服务端；只有生成等模型调用需要连接团队网关。

重新打开这个方向的理由有三条：

- **内网 HTTP 页面不是安全上下文，浏览器剪贴板不可靠。** 页面里 `navigator.clipboard` 就是 `undefined`，读只能靠原生 paste 事件、写只能靠选中内容后触发已废弃的复制命令，真实图片的复制与粘贴因此一直受浏览器与部署形态摆布（[ADR 0021](0021-clipboard-paste-dispatch-by-clipboard-content.md)）。这条限制来自 Web 部署形态本身，把页面套进桌面窗口不会消失，而把画板上的图片交给 Word、微信和 PS 正是美术每天要用的动作。
- **画板与任务目录要回到本机。** 任务目录是生成结果、参考图快照与结局记录的唯一真源（[ADR 0010](0010-task-directory-is-the-source-of-truth-boards-are-views.md)），Web 路线把它放在服务端，代价是服务端不做备份、用户数据根是唯一副本、还要靠闲置用户与未引用任务目录的清理规则兜底容量（ADR 0018）。本地优先下这份用户数据根由客户端管理，一台电脑一份，换一把 new-api API 密钥不改变可见的本地画板。
- **现有 React 画板能力要保留。** 画板、生成任务、撤销与画板包（[ADR 0013](0013-board-pack-as-exchange-format.md)）的语义已经成型，换壳不该重写画板，也不该让用户重新学一遍操作。

技术选择：固定 MyGo `v0.9.0` 及其配套 CLI，桌面壳与本地核心用 Go 重写；**不使用 Rust sidecar**，也不保留任何 Rust 进程；**不做 Go 原生 UI**，继续复用现有 React / React Flow 画板与任务核心。原生能力（系统剪贴板、用户数据根、画板文件读写、画板包导入）只经现有前端壳端口进入，React 不直接依赖 MyGo 绑定细节；MyGo 的生成绑定是该端口的生产适配器，不形成第二套前端调用链。现有 Rust 实现只作为行为与测试参照，不进入新客户端。

剪贴板决定的前提被修正：[ADR 0021](0021-clipboard-paste-dispatch-by-clipboard-content.md) 里「页面跑在内网 HTTP 上、不是安全上下文，因此读只能靠 paste 事件、写只能靠复制命令」这一段只适用于 Web 路线。桌面客户端由 Go 原生系统剪贴板读写文本与 PNG 图片，页面安全上下文、浏览器焦点与 Web Clipboard API 权限都不是成功条件；ADR 0021 定下的画板层语义不变——Ctrl+V 仍由系统剪贴板里的内容决定粘节点还是粘图片，Ctrl+C 仍由选区决定复制图片还是复制节点，节点标记、图片优先规则、单选图片复制、多选节点复制、部分成功、单张 64 MiB、一个撤销步、落点、不自动接线与「导入参考图」链路都照旧。

效率调研（[MyGo Go 壳与当前 React / Rust Web stack 的开发效率调研](../research/mygo-vs-current-stack-efficiency.md)，提交 `2f4fdf2a57e28d1eed1de4517386e660921923a2`）是这份决定的证据之一，但只到「支持继续验证 MyGo」为止：它测的是最小 MyGo 壳与当前 Rust 服务端的构建时间，也记录了 typed binding、单命令 dev、打包与 updater 上的功能收益，同时明确最小壳没有移植任何业务，全业务等价的 cold / warm / 增量时间、包体、冷启动与内存都仍是未知。**本决定不声称全量重写已有性能优势**，也不拿最小壳的数字推算完整产品的收益。

第一竖切（[#124](https://github.com/qinyuanj/kacha/issues/124)）交付一个可运行的 Windows 客户端：用 Go 原生剪贴板读写文本与 PNG 图片；在本机建立并管理一份用户数据根（默认位置可用，位置被记住，内部文件由客户端管理）；打开与新建保存在其中的本地画板，编辑后原子保存、失败保留旧内容与内存中的未保存改动；导入一个用户手动导出的画板包，使其在本地继续显示与编辑，导入限制在目标用户数据根内并拒绝路径越界。画板的节点、连线、撤销、复制粘贴与生成任务交互保持原语义；本切片还没有生成能力时，界面要清楚区分「画板可编辑」与「生成尚不可用」，不得把未实现动作伪装成已成功。

明确不在本切片内：生成任务的网关调用、结果下载与结果落盘、图层拆分执行与任务队列迁移；闲时自动更新、签名发布、安装器升级与 Gitea 发布链；自动整用户迁移、服务端数据对账、Web 冻结与 Web 关闭；多设备同步、冲突合并、账号体系与系统凭据库；用户自行选择或搬移用户数据根的完整存储管理界面；macOS 与 Linux 的实现、构建和验收；包体、启动时间、内存与完整业务编译速度的最终结论。本决定不新增服务端接口，也不修改现有 Web 服务端的数据模型。

## Considered Options

- **继续 Web 路线，在浏览器里绕开剪贴板限制**：否决。内网 HTTP 下 Web Clipboard API 根本不存在，剩下的只有原生事件与已废弃的复制命令，浏览器将来移除它时复制图片会一起失效；这是部署形态的限制，不是可以靠适配层补掉的缺口。
- **把现有页面套进桌面窗口（Tauri 过渡壳或浏览器外壳）**：否决。套壳只换窗口不换权限来源，普通浏览器里的内网 HTTP 限制仍在；而 Tauri 壳意味着继续维护 Rust 进程，与「不保留 Rust sidecar」直接冲突。
- **MyGo + 现有 Rust sidecar**：否决。它能降低业务重写风险，但 Rust 业务改动仍走 Cargo，仍要按平台分发 Rust helper，进程生命周期、loopback 访问控制与两个二进制的更新都要新验收；第一竖切要的是单一 Go 工具链，不是再养一套 Rust 进程。
- **用 Go 原生 UI 重写画板**：否决。画板是本产品最贵的资产，节点、连线、撤销、区域指示与画板包语义都在 React 侧成型；重写等于把第一竖切变成不可运行的全量替换。
- **跟随 MyGo `main` 而不是固定 tag**：否决。调研记录的源码快照在 `v0.9.0` 之后，官方版本发布密集且 native modules 明确允许 breaking change；不固定版本就无法复现第一竖切，也无法把「测的是哪份代码」写清楚。
- **先做全量 Go 移植再交付**：否决。全业务等价的编译与测试证据都还没有，先交付一个可运行切片才能验证剪贴板、用户数据根与画板包导入这三件真正影响使用的事。

## Consequences

- ADR 0018 的 Web 部署形态（服务端用户数据根、密钥指纹身份、7 天会话 cookie、服务端清理与回收区、服务端不备份）不再是路线约束；其中仍然成立的领域决定（任务目录为真源、画板包是交换物、画板位与归档）继续有效，但它们作用在本机的用户数据根上。
- 剪贴板能力不再受页面安全上下文约束，但桌面侧要自己承担真实系统剪贴板的失败面：剪贴板被其他程序占用时给出可重试的失败，HEIC、TIFF 这类不受支持的格式在复制侧明确失败并指向节点已有的「另存为…」，复制图片不改画板、不新增节点、不构成撤销步。真实系统剪贴板只能由 Windows 真机与外部软件验收，合成事件全绿不算位图已写入。
- 用户数据根由客户端管理，一台电脑一份，API 密钥不参与本地画板身份、不写进画板、普通设置或日志；换密钥后本地画板仍可见。画板包导入是第一竖切唯一的数据迁入方式，不连接旧服务端、不扫描服务端数据根、不提供整用户迁移。
- MyGo 版本固定意味着升级要单独验证：CLI、automation CLI 与 WebView2 Runtime 都要记录版本，升级后重新跑第一竖切的行为验收，不能跟随 `main` 漂移。
- 桌面 e2e 需要重新建立：浏览器里跑通的 Playwright 闭环不能直接当作桌面验收，页面在普通浏览器里没有 MyGo runtime。自动化仍覆盖事件适配、分派与画板结果，真实剪贴板与窗口行为留给真机。
- 这条路线把发布形态也换了回来：桌面安装包、签名与闲时自动更新属于后续竖切，本决定不承诺它们的做法；ADR 0007、0016、0017 里针对旧桌面版的细节仍处于被 ADR 0018 取代的状态，要等相应竖切再单独记录。

> 2026-11-15 真机验收补记（[#132](https://github.com/qinyuanj/kacha/issues/132)）：用固定版本的 release 构建（MyGo 0.9.0 / go1.27.3 / WebView2 158.0.4370.21）在 Windows 11 真机上验收第一竖切。
>
> 已验证：
> - 能力边界：画板可编辑（提示词 / 参考图入口可用、可新建节点），生成、运行、整理都标「（尚不可用）」并置灰，能清楚区分「画板可编辑」与「生成尚不可用」。
> - 画板包导入：构造合法的 v2 `.ugcpack`（含节点、连线、图片与两个图层文件），经桌面客户端「画板包 → 导入画板包…」导入后，新画板带着提示词、参考图、生成任务、结果节点（2 图层）与连线重新打开，图片正常显示；导入结果落在用户数据根（`画板/`、任务目录、`导入参考图/`），桌面客户端全程不依赖服务端。
>
> 验收中发现并修复的缺陷：WebView2 的页面来自 `http://mygo.localhost`，不允许这种 http 页面加载 `file://` 子资源；桌面端口原来把节点图片地址写成 `file:///…`，导致画板里所有图片显示「图片缺失」。改为在启动时把用户数据根经 `mygo.Protocol` 注册成自定义协议 `kacha`，页面用 `http://kacha.localhost/<相对路径>` 取图（见 `desktop/wiring.go` 的 `registerAssetProtocol` 与 `client/src/shell/desktopStores.ts` 的 `servedFileUrl`）。因此本机文件不能交给页面用 `file://` 读，这是本竖切的实现约束。
>
> 已知限制：真实系统剪贴板只能在已解锁的交互会话里验收。会话锁屏时 Windows 拒绝后台进程访问剪贴板（`clip.exe` 返回 `Access is denied`，`OpenClipboard` 返回 `ERROR_ACCESS_DENIED`=5），此时既不能投递外部截图，也不能验证复制成功 / 失败面。
>
> 未实测：外部截图粘贴进画板、画板图片复制到 Word / 微信、透明 PNG 的 alpha、剪贴板被占用时的可重试失败、HEIC/TIFF 复制失败的提示、Word / 微信里的真实粘贴结果，以及焦点许可下客户端复制粘贴动作的真实剪贴板观察——验收时会话锁屏、剪贴板不可访问，均记为未实测，待会话解锁后按 #132 矩阵补测。Adobe Photoshop 本机未安装，无法实测。
