# 质量门禁只检查本次改动

质量范围取目标分支与 HEAD 的 merge-base 以来的改动，加上工作区改动，再限定在 `uml-quality.json` 声明的源码范围。基线缺失或工具出故障均明确失败，不把空结果当通过。

CRAP 超过 10 或缺少覆盖率、重复相似度达到 0.8 且至少一边属于改动文件都不通过。CRAP 和重复检查进入默认验证；`verify.py --quality` 是合入集成分支前的发版门禁，跑的是同一组步骤，不再追加变异测试。

只查改动避免维护全仓库基线，也要求本次触及文件的存量问题一起负责。指标与覆盖率快照只作本次验证产物，不提交。工具来源和变异副本约束见 ADR 0022，验证命令见 [构建说明](../../packaging/README.md)。

## 2026-11-20：变异测试不进门禁

owner 决定不做变异测试，发版门禁因此不含变异测试。质量脚本每次运行都打印一行「变异测试未启用」并给出原因，不静默跳过：静默会让人以为跑过了。

两条原因各自都足以让这条路走不通：

- 本机 Windows commit limit 只有 23,060 MB（物理内存 16 GB 加 6.8 GB pagefile），`--mutate` 的变异工作副本会把整机拖崩。
- uml-viewer 当前构建的 mutator 产不出覆盖率产物，所有变异体都被算成未覆盖（#184 因此关闭）。

已接受的后果：改了逻辑没补测试不再有自动检查兜底，只能靠人和复审。

判定逻辑不动：存活变异体与未覆盖变异点仍是 `quality.py --mutate` 的拒绝条件，代码与单测都保留，只是当前没有调用方（`verify.py` 不再传 `--mutate`）。恢复需要同时满足：本机内存与 commit limit 够跑变异工作副本、mutator 能产出可信的覆盖率产物、owner 重新确认这两条前提；届时在 `verify.py` 的 `commands()` 里重新拼上 `--mutate`，并改回本节。
