# 跨语言共享 schema 与代码生成

画板包接口的结构（`ExportSpec`、`MergeUnit`、`EntryFact` / `PackEntryFact`、`MergeReport` 等）在 Rust 服务端、TS client 和 `packaging/load_users.py` 里各写一份。项目不引入共享 schema，也不从 schema 生成三端类型。

## 为什么不做

**契约已经由真实端到端测试守住。** `client/e2e/web/packs.spec.ts` 用真实的 TS client 调真实的 Rust 服务端，覆盖导出、条目信息、问已有、按内容上传、合并结果、v1 和 v2 包格式，以及旧桌面版包的导入。任何一端改了字段名、可空性或枚举值，这些用例会直接失败。schema 生成能防住的错误主要是字段名和类型写错，这里已经都能抓到；而 e2e 还能测到 schema 表达不了的语义，比如重复内容只上传一次、读不了的身份文件视为不同。

**没有发生过漂移。** 截至 1.2.0，服务端画板包代码共有 20 次提交，其中 11 次同时改了 client 的对应代码。这 11 次提交和 issue 记录里，都没有一次是在修两端结构对不上的问题。

**生成链的成本是持续的。** 三种语言各要接一个生成步骤或依赖，生成器还得在原生 Windows 的构建、`packaging/verify.py` 和 pre-push 验证里跑通。每个新贡献者和每个新 worktree 都要付这份成本，而它换来的保障现有测试已经提供了。

`load_users.py` 不跑 e2e，是唯一没有被持续验证的使用方。它是压测脚本，结构漂移会在下次运行压测时暴露，不会进入生产。删除 v1 请求体时（#81），它会迁到当前请求体，并对测试服务端跑通一次导入。

## 什么时候值得重新考虑

- 出现第一次真实的跨端结构漂移，而且现有测试没有拦住。
- 接口出现第四个独立使用方（例如第三方工具），或者需要对外发布接口文档。
- 接口结构的变更频率明显上升，手工同步三端成为常见的返工来源。
